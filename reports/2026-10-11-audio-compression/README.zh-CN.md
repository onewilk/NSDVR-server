# 音频压缩测试（2026-10-11）

[English](README.md)

测试 NSDVR 扩展的各种音频编码在主机上要花多少 CPU，以及能不能减少丢帧。原始数据在 [`data/`](data/)；摘要已发到
[SysDVR #402](https://github.com/exelix11/SysDVR/issues/402#issuecomment-6106541472)。

## 结论摘要

- **CPU**：马车 8 比赛中，PCM 串流时 3 号核心占用 59.3%。24 kHz PCM 和 IMA ADPCM 不额外占用（−0.4 个百分点），
  Opus 64 kbps / 复杂度 0 多 1.2 个点，Opus 96 kbps / 复杂度 5 多 1.7，Opus 128 kbps / 复杂度 10 / 10ms 帧多 4.6。
  游戏用的 0～2 号核心始终不变。
- **网络好时没什么可改善的**：手机 5GHz 热点或路由器在附近时，实际游玩中不管哪种编码几乎都不丢帧（0～0.7%；
  王国之泪 0.06%）。
- **网络临界时 Opus 效果明显**：丢帧多少取决于串流码率超出 Wi‑Fi 链路承载能力多少。画面本身约 5Mbps，
  加 PCM 是 6.5，24 kHz 是 5.75，Opus 64k 是 5.07。链路在 5.3～5.7Mbps 时，PCM 丢 17～23% 的帧，Opus 只丢 0～9%。
  低于约 5Mbps 时什么编码都没用。
- **马车 8 的模式选择菜单**每 30 秒让 3 号核心满载约 0.5 秒，SysDVR 每次丢约 1 秒画面。不串流时也有，停掉其他所有
  系统模块也有；比赛中和其他游戏里没有。和 SysDVR、网络都无关。
- **建议**：压缩选项保留 Opus 64 kbps / 复杂度 0（音质优先可加 96 kbps / 复杂度 5，24 kHz PCM 作为零 CPU 备选）；
  去掉 ADPCM 和高复杂度 Opus。

## 测试环境

| | |
|---|---|
| 主机 | Switch，系统 22.5.0，大气层。CPU 1020MHz（sys-clk）；它的自动加速会对菜单尖峰做出反应，见下文 |
| 客户端 | 华为 Mate 90 Pro Max 上的 NSDVR 调试版，TCP Bridge，平滑「延迟优先」，网络优化开启 |
| 网络 | 手机的 5GHz Wi‑Fi 直连热点（36 信道），或 5GHz 路由器；「弱网」= 主机放到离路由器较远处 |
| 游戏 | 马车 8 豪华版（模式选择菜单；大奖赛，开智能转向和自动加速），塞尔达传说 王国之泪 |
| 版本 | [`perflog`](../../PERFLOG.md) = 上游 master + 记录器，`nsdvr` + 记录器（`make PERFLOG=1`），不带记录器的 `nsdvr` |

### 方法

- 仅测试用的记录器（[PERFLOG.md](../../PERFLOG.md)）在主机上每秒写一行：4 个核心各自的占用（每个核心固定一个线程读
  空闲时间，和 Status Monitor 相同）、SysDVR 线程 CPU、发送字节数、当前音频编码、频率、剩余内存。它自身的 CPU 也会
  记录（平均 0.007%）。
- 客户端每秒往 `stats.csv` 写一行，包括扩展的诊断数据（grc 断档、发送阻塞）。
- 客户端的自动轮换每分钟切换一次编码；两边的记录都带编码，同时用来对齐主机和手机的时钟
  （[`tools/perf_report.py`](https://github.com/onewilk/NSDVR/blob/main/tools/perf_report.py)）。
- 每次切换后的前 3 秒、3 号核心尖峰前后 1 秒，以及比赛中的读盘画面都不计入。

## 结果

### 静止菜单画面下的 CPU（马车 8，3 号核心占用 %，已去掉尖峰）

| | 3 号核心 | 音频线程 |
|---|---|---|
| 不串流 | 54.0 | – |
| 上游：只有画面 | 59.1 | – |
| 上游：画面 + PCM | 62.4 | 0.1 |
| 扩展：PCM | 63.7 | 0.1 |
| 扩展：24 kHz | 63.4 | 0.3 |
| 扩展：ADPCM | 63.1 | 0.6 |
| 扩展：Opus 64k c0 | 64.2 | 2.1 |
| 扩展：Opus 96k c5 | 65.6 | 3.7 |
| 扩展：Opus 128k c10 10ms | 67.3 | 5.5 |

画面约占 3 号核心 5 个点，PCM 声音约 3 个点。上游两行来自另一次开机；扩展的 PCM 高 1.3 个点，可能是诊断功能的开销，
也可能是两次开机之间的波动。

### 比赛中的 CPU（马车 8，轮换两轮，每种编码约 100 秒）

| | 3 号核心 | 比 PCM | 音频线程 | 编码 ms/s | 发送 kbps |
|---|---|---|---|---|---|
| 不串流 | 47.7 | | | | 0 |
| PCM | 59.3 | | 0.1 | 0.0 | 6486 |
| 24 kHz | 59.0 | −0.4 | 0.3 | 3.8 | 5772 |
| ADPCM | 58.9 | −0.4 | 0.6 | 8.2 | 5385 |
| Opus 64k c0 | 60.5 | +1.2 | 2.1 | 37.0 | 5066 |
| Opus 96k c5 | 61.1 | +1.7 | 3.7 | 58.8 | 5107 |
| Opus 128k c10 10ms | 63.9 | +4.6 | 5.9 | 93.3 | 5090 |

95% 置信区间都在 ±0.4 个点以内。各编码下 0～2 号核心约 50% / 37% / 30%。「不串流」只有约 30 秒的比赛样本。

### 网络良好时的丢帧

| 测试 | 时长 | 丢帧 |
|---|---|---|
| 马车 8 比赛，路由器，全部编码 | 12 分钟 | 每种编码 0～0.7% |
| 马车 8 比赛，路由器，PCM | 4 分钟 | 1 帧 |
| 王国之泪，热点，PCM | 4.6 分钟 | 5 帧（0.06%） |

### 马车 8 模式选择菜单：每 30 秒一次 3 号核心尖峰

- 每 30 秒，3 号核心被占满约 0.5 秒（sys-clk 随后把 CPU 拉到 1785MHz，这是反应，不是原因）。尖峰期间 SysDVR 的
  发送卡住 225～690ms，grc 丢帧。
- 第一轮里，全部 19 次超过 200ms 的发送卡顿、584 个丢帧中的 577 个，都在尖峰前后 1 秒内。
- 以下情况都照样出现：不串流；停掉其他所有系统模块（SaltyNX、sys-clk、风扇调速、emuiibo、MissionControl、
  sys-KeyX、NxThemes，只留 sys-patch 和 nx-ovlloader）；不带记录器（普通 `nsdvr`：每 30 秒卡一次，每次 26～31 帧，
  占全部丢帧的 92%）；改用路由器。
- 主菜单、比赛中、王国之泪里都没有。

### 弱网（主机远离路由器，PCM / 24 kHz / Opus 64k 每分钟轮换）

每个 1 分钟时段的丢帧率（按时间顺序）：

| 轮次 | PCM | 24 kHz | Opus 64k |
|---|---|---|---|
| 1 | 0.1、2.3、0、**63.2**、17.9 | **27.8**、0、2.2、**48.0**、0.9 | 0、0、0、5.8、0.6 |
| 2 | 12.9、17.4、23.5、23.0、23.4 | 1.3、2.0、12.9、37.4 | 0.1、2.3、9.4、**62.4** |
| 合计 | 16.0% / 21.3% | 15.8% / 14.3% | **1.3%** / 18.6% |

第 2 轮主机实际发出的速率（记录器），对比各编码的需要：

| | 需要 | 实际发送（占需要的比例） | 丢帧 |
|---|---|---|---|
| PCM | 约 6.5Mbps | 5.3～5.7Mbps（81～87%） | 17～23% |
| 24 kHz | 约 5.75Mbps | 5.7 → 5.1Mbps（99% → 89%） | 1～2% → 13% |
| Opus 64k | 约 5.07Mbps | 5.1 → 4.6Mbps（100% → 90%） | 0～2% → 9% |

第 2 轮 Opus 那个 62% 的时段，链路崩到 1.4～2.5Mbps（还断线重连了一次），所有编码都扛不住。和紧挨着的前后时段比，
9 次里 Opus 7 次更低（1 次持平；1 次更高，就是链路崩溃那次）。

## 结论

1. 扩展的各种编码在 3 号核心上都很便宜；低复杂度 Opus 约多 1 个点，从不影响游戏核心。
2. 链路良好时不丢帧，压缩没有区别。链路在约 5～6.5Mbps 时，Opus 64k（比 PCM 少 1.4Mbps）决定了流畅还是卡顿；
   24 kHz 只省 0.75Mbps，效果较小。低于 5Mbps 时光画面就装不下。
3. TCP 本身没有表现出问题：只要链路装得下（Opus 达到需要的 98～100%），几乎不丢帧（0～2%）；网络良好时游戏中也没有
   发送卡顿。看到的丢帧要么来自链路容量，要么来自主机 CPU（菜单尖峰），换传输协议都解决不了。所以从这些数据看，
   UDP 模式没有必要。
4. 客户端的网络预警只能看到手机自己的 Wi‑Fi 链路：弱网测试中它一直报告「正常」，因为弱的是主机那一侧的链路。

## 局限

- 只有一台主机、一部手机、两款游戏；菜单尖峰只在马车 8 上看到。
- 弱网测试依赖一条容量会变化的链路；结论依据的是各编码之间一致的排序和发送速率证据，而不是合计百分比。
- 本次没有测听感（ADPCM 在芯片音乐上的噪声见之前的离线评估）。
